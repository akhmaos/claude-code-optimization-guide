# Практические советы по оптимизации токенов

20+ конкретных стратегий, организованных по степени влияния.

## Высокое влияние

### 1. Напишите CLAUDE.md
Поместите контекст проекта, стандарты кода и паттерны в `CLAUDE.md` в корне проекта. Это избавит вас от повторного объяснения каждую сессию.

```markdown
# CLAUDE.md
Next.js 14 приложение с TypeScript, Prisma ORM, PostgreSQL.
- Тесты: `npm test`
- Dev сервер: `npm run dev`
- Миграции: `npx prisma migrate dev`
- Доступ к БД: `src/lib/db.ts`
```

**Экономия**: 200-500 токенов за сессию.

### 2. Указывайте конкретные пути

```
Плохо:  "Найди код аутентификации"          → несколько поисков
Хорошо: "Read src/auth/middleware.ts"        → одно чтение
```

**Экономия**: 3,000-30,000 токенов на каждый избежанный размытый запрос.

### 3. Запускайте `/compact` проактивно

Не ждите авто-компакта на 167K. Закончили задачу — сжимайте:

```
/compact сохрани изменения API, забудь исследование тестов
```

### 4. Ставьте бюджеты токенов

```
Исправь null pointer в auth.ts +500k
```

### 5. Используйте субагенты для исследований

```
Плохо:  "Помоги понять как работает кэширование"
        (20 файлов в основном контексте = 100K токенов)

Хорошо: "Используй Explore агент чтобы понять кэширование"
        (агент читает файлы, возвращает 500 токенов)
```

## Среднее влияние

### 6. Читайте файлы с offset/limit

```
Плохо:  "Read src/services/auth.ts"          → все 2000 строк
Хорошо: "Read src/services/auth.ts строки 45-80" → 35 строк
```

### 7. Grep/Glob вместо Bash

```
Плохо:  "Запусти: find . -name '*.ts' | xargs grep 'TODO'"
Хорошо: "Grep 'TODO' в *.ts файлах с head_limit 20"
```

### 8. Держите сессии стабильными

Каждое ломание кэша стоит денег:
- Не переключайте модели среди сессии
- Не тогглите fast mode без нужды
- Не перезапускайте сессии

### 9. Будьте конкретны в промптах

```
Плохо:  "Исправь баг"
Хорошо: "Исправь null check на строке 42 в src/auth/validate.ts"
```

### 10. Используйте Plan Mode

Для сложных задач — сначала plan mode:
- Read-only исследование (без лишних правок)
- Согласование подхода до написания кода
- Меньше откатов

### 11. Группируйте связанные вопросы

```
Плохо:  "Что делает функция A?" → "Что делает B?" → "Как они связаны?"
Хорошо: "Объясни функции A и B в src/utils.ts и как они связаны"
```

### 12. Ограничивайте вывод Bash

```
Плохо:  "Запусти npm test"                → 500 строк
Хорошо: "Запусти npm test 2>&1 | tail -20" → 20 строк
```

## Меньшее влияние (но накапливается)

### 13. Не просите объяснять сделанное
Claude Code показывает диффы. Не спрашивайте "что ты изменил?" — читайте дифф.

### 14. Избегайте лишних подтверждений
Не спрашивайте "ты уверен?" — каждое подтверждение = ещё один API-вызов.

### 15. Используйте слэш-команды
```
/commit    → оптимизированный workflow коммита
/compact   → ручная компрессия контекста
```

### 16. Не читайте документацию без нужды
README.md, CHANGELOG.md — часто большие и редко нужны для кодинга.

### 17. Целевые git-команды
```
Плохо:  "Покажи git log"                → полная история
Хорошо: "Покажи последние 5 коммитов"   → фокусированный вывод
```

### 18. Закрывайте темы явно
```
"Фикс авторизации готов. Теперь работаем над API эндпоинтом."
```

### 19. Переиспользуйте контекст
Связанные задачи — в одной сессии, не в разных.

### 20. Следите за расходами
`/cost` регулярно. Если стоимость высокая — вы работаете неэффективно.
